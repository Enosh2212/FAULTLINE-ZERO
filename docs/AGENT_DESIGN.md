# FAULTLINE ZERO — Autonomous Agent Design & Orchestration

## Overview
FAULTLINE ZERO implements `ToolInvestigator`, an autonomous, tool-calling investigation agent built for graph-native software intelligence. The agent operates under strict safety and execution boundaries, utilizing high-speed LLM inference (Groq GPT-OSS 120B / `llama-3.3-70b-versatile`) while maintaining a mathematically sound deterministic fallback.

---

## 1. Execution Modes & Provider Configuration

The agent supports three execution modes via `POST /api/v1/git/investigations`:

1. **`auto`**: Default mode. Checks for live provider configuration (`GROQ_API_KEY`, `GROQ_BASE_URL`, `GROQ_MODEL`). If configured and verified, launches the autonomous model tool loop. If unconfigured or unavailable, automatically falls back to the deterministic graph pathfinder and flags the report explicitly as `deterministic_fallback`.
2. **`model`**: Enforces strict LLM tool calling. If credentials are missing or the provider fails, the investigation halts with `PROVIDER_UNAVAILABLE` or `INVESTIGATION_ERROR`. It will never secretly switch to deterministic mode and lie about autonomy.
3. **`deterministic`**: Bypasses LLM tool calling entirely, executing algorithmic FalkorDB graph traversal and invariant resolution. Ideal for air-gapped CI environments and zero-cost local runs.

---

## 2. Tool Inventory & JSON Schemas

The model is given access to an allowlist of seven bounded, functional tools. Each tool is strictly defined using Pydantic JSON schemas:

1. **`get_git_diff`**:
   - *Arguments*: `change_id: str`
   - *Behavior*: Extracts the unified Git diff and parsed AST symbols between baseline and candidate branches.
2. **`trace_impact_graph`**:
   - *Arguments*: `symbols: List[str]`
   - *Behavior*: Traverses FalkorDB from modified symbols through call chains (`CALLS*1..3`) to find connected services and business invariants.
3. **`find_relevant_tests`**:
   - *Arguments*: `invariant_ids: List[str]`
   - *Behavior*: Queries FalkorDB to find existing test fixtures (`:KnownTest`) mapped to the identified invariants.
4. **`recall_investigation_memory`**:
   - *Arguments*: `symbol_id: str`
   - *Behavior*: Retrieves past investigation history, recurrence frequency, and previous regression traces for the symbol.
5. **`synthesize_counterexample`**:
   - *Arguments*: `invariant_id: str, scenario_spec: ScenarioSpec`
   - *Behavior*: Constructs a bounded, schema-validated test scenario for invariants lacking pre-existing test coverage.
6. **`compare_revisions`**:
   - *Arguments*: `scenario_or_test_id: str`
   - *Behavior*: Concurrently executes the test scenario against both baseline and candidate Git revisions in isolated subprocess sandboxes and returns dual observations.
7. **`finalize_investigation`**:
   - *Arguments*: `verdict: str, evidence_summary: str`
   - *Behavior*: Validates that all observations satisfy the differential oracle policy and records the final deployment gate decision in FalkorDB.

## 3. Graph-Guided Counterexample Discovery

When a code change touches an invariant that has no known test (`MATCH (b:BusinessInvariant) WHERE NOT (b)-[:COVERED_BY]->(:KnownTest)`), standard CI suites pass blindly. 

FAULTLINE ZERO's signature capability synthesizes an executable `ScenarioSpec`:
1. **Rule Discovery**: FalkorDB locates the unasserted invariant (e.g., `INV-REFUND-01`: "Refund balance idempotency & ledger consistency").
2. **State Space Exploration**: The agent analyzes method parameters (e.g., `process_refund(order_id, amount, idempotency_key)`).
3. **Constrained Generation**: The agent generates a concrete operational scenario (e.g., dispatching duplicate refund requests with identical or missing idempotency tokens).
4. **Validation**: The synthesized scenario is validated against a strict Pydantic schema before execution. Unsafe shell calls, arbitrary imports, or external network requests are strictly rejected.
5. **Differential Execution**: The generated scenario executes on both revisions. If baseline succeeds ($90.00 ledger balance) and candidate fails ($80.00 double deduction), a **reproduced regression** is proven on an invariant that had zero pre-existing test coverage.

---

## 4. Safety Boundaries, Budgets & Recovery

- **Iteration Budget**: Hard-capped at 16 iterations (default max 6 in production).
- **Time Budget**: 120 seconds wall-clock budget. In-flight subprocesses terminate after 8 seconds.
- **Token Limits**: Request timeouts at 20 seconds. Prompt payloads are capped to prevent context overflow.
- **Zero Hallucination Tolerance**: Free-form prose generated by the LLM is discarded. The agent cannot assert verdicts; verdicts are derived solely from differential execution observations (`baseline_passed == True && candidate_passed == False`).
- **Resilient Fallback**: Any malformed tool call, JSON syntax error, or provider outage triggers an immediate safe recovery without crashing the server.

## Source-backed project context (implemented)

Before the bounded tool loop starts, the persistent repository retrieves revision-scoped project context through `ProjectContextService`. The actual `retrieve_project_context` step is recorded; the package is stored on the report and supplied to the model as untrusted data. Source/documentation text cannot change the system policy or expand allowed tools. Typed empty arguments expose the bounded context again if requested; no model-supplied path, script, shell or Cypher is accepted.

The package separates source facts, explicit approved invariants, hypotheses, unknown dependencies and historical execution. Legacy graph plans and uncovered rules are filtered against approved context IDs. Counterexample generation also requires a connected approved uncovered invariant. Missing trustworthy context yields coverage gaps and an inconclusive report rather than guessed rules. Known sample scenarios still use the existing controlled runner and evidence-derived verdict policy.

See PROJECT_CONTEXT_ARCHITECTURE.md, INVARIANT_REGISTRY.md and CONTEXT_GRAPH.md for implemented trust boundaries. A scripted model protocol test checks that the model receives the package; live Groq provider quality is not inferred from that test.
